# キャラクター移行計画 revision 6 — 利用者経路・評価・本番配備までの接続

2026-09-14。オーナーの「局所改善を止める」「計画を修正する」という指示を反映した計画修正。アプリ実装・公開・本番切替の完了記録ではない。

## 目的と変更範囲

受入済み共通基盤要件v3、キャラクター要件v5、ADR-0031を維持する。
小分けに生成・検証・修復する共通基盤を、作成・改訂・V2からV3への移行で実際に使う。
構造・意味の全体整合性、保護対象の維持、所有者による候補受入、世代の不変性を維持する。
既存V2の一括生成の修復追加を、この目的の代わりに進めない。

実行順序は次のとおり。

1. `cc304`: 実provider driverと作成・改訂worker、移行entrypointをkernelへ接続する。質問回答・再試行の認証済みAPI/UI、安全な候補と意味差分の表示、別操作としての最終受入まで含める。実コードを通る制御HTTP応答で、三つの利用経路、回復、上限到達、回答後の自動処理、元情報からの再試行、候補または失敗の保存まで確認する。workerや部品テストだけでは完了しない。
2. `cc305`: 接続済み候補をレビューする。既存R20が要求する代表ケース・数値基準・評価予算のオーナー判断を準備し、実評価前に確定する。旧経路との整合確認もここで行う。別途認められた外部操作で新しいStage用revision/tagを確定する。rc12の再利用で接続済みと扱わない。
3. `cc306`: 合意した代表ケースで実provider・Stage評価を行う。自動完了、生成品質、整合修復、元情報・保護対象の維持、不要／重複質問、後段の手戻り、checkpoint待ち、遅延、呼出数、tokens・費用、最終意味品質を測る。失敗も保持し、smoke成功だけで完了しない。本番のpolicy・pointer・trafficは変更しない。
4. `cc307`: 別途認められた本番配備操作で、Stage確認済みbackend/frontendと必要な互換storage変更を配備し、実revision、V2/V3 reader、移行経路、利用者API/UI、rollbackを読み戻す。既存policyとpointerは維持する。共有インフラの分離は行わない。
5. `cb209`〜`cb214`: 本番配備確認後に対象を新鮮な状態で確定し、同じfocused移行経路で候補生成、候補受入、append/CAS、復旧確認、新規作成・改訂のV3切替を行う。`cb214`は`cc305`と`cc307`の証拠を引き継ぎ、driftを確認する。

`ca104`は独立タスクから削除し、旧経路の整合確認を`cc305`と`cb214`へ吸収した。
その専用の中間到達点`cm103`も削除した。必要な確認を省いたのではなく、重複実行を除いた。
本番配備を先に置くのは、新しいV3世代のpointerを旧readerへ公開しないためである。
新規policyの有効化は引き続きB14であり、コード配備とは区別する。

Stageと本番の共通部分を共有し続けるという決定は変更しない。
接続作業6p、評価2p、本番配備1pは仮見積りであって実績や日程保証ではない。
接続箇所とオーナーが決める評価ケース数に応じて更新する。数値評価基準は本計画で創作しない。

## perttool調査結果

対象は実行中のインストール済みCLI（出力上tool_version=0.11.0、CLI Contract10）。
最新版一般や別環境の実装についての断定ではない。

| 機能 | 修正前の観測 | 検査できること・できないこと |
| --- | --- | --- |
| DAG・resource解析 | check成功、next候補なし、cc302のみactive | 登録された依存・資源を検査する。省略された実装作業は生成しない |
| Plan assurance | analyze/nextのcoverageはnot_enabled | 宣言された計画基準の変化を検知する。誤った計画そのものの正しさは証明しない |

| Planning Pool | 修正前はWorkなし | インストール済みguideはFinal Goalの網羅性を証明しないと明記している |
| 専用assurance照会 | 同じ元ファイルのplan-assurance showがPTDSL-003で失敗 | document checkとの不一致が実在する。過去にこのエラーが起きていた証拠ではない |

追加で確認した具体的な実装事実:

- `dist/assurance/evaluate.js` の未設定分岐は `ok: true`、`coverage: not_enabled`、空のdiagnosticsを返す。
- `dist/assurance/source.js` のtaskContractは `source` を文字列として取り込む。ファイル名をsourceに書くだけで参照先本文の要件適合を検証する処理ではない。
- インストール済み `perttool guide planning-pool --level detail` は、Goal Obligation / Coverage / Sealを別の将来作業として説明している。GitHub Issueの現在状態を確認したという意味ではない。
- 元ファイルに対する `plan-assurance show` は353行目の長いIDのwork_eventでPTDSL-003。`document check` は同じファイルを受理する。これを今回の計画修正でツール更新や履歴削除により隠さない。

## 因果の区別

計画の欠落を作った条件は、部品完成を終点とした分割で、受入済みの実利用成果を
後続の実行作業に引き継がないまま次の運用段階へつないだこと。
検出されなかった条件は、任意の検証が未設定であったことと、各validatorの
対象が宣言済み構造・基準に限られること。後者を欠落の発生原因と混同しない。

「機能が入っている」「Grammar9である」「ok=true」から、要件の網羅性を
検証済みとは言えない。全過去taskを一括sealしても、欠落した計画を固定するだけに
なり得るため、過去の成果受入を捏造して有効化していない。

この調査は、計画表現とツール適用の不一致を立証した範囲に限る。
エージェントが指示から繰り返し逸脱する根本原因全体や、専用照会のparser不一致の
完全な原因は未確定。CLI LLMThink監査は推論の整合確認であり独立した事実証明ではない。

条件の登録は実装完了でも所有者の成果受入でもない。

検証は `document check`、`dag analyze --schedule both`、`dag next --format json`。
確認対象は、次候補が`cc304`、接続・評価・配備・最終成果のacceptanceがpending、
旧試験が実行候補ではないこと。形式検査合格を再発防止の実効性観測とは扱わない。

次回の実装では、この実行作業のsourceから本書と受入済み要件へ戻れる。
完了判定は三つの実利用経路の証拠による。将来の作業で実際に逸脱を防げたかは未観測。
