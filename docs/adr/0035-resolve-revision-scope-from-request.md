# ADR-0035: 修正依頼文から変更範囲を解決する

- Status: Accepted
- Revision: 2
- Date: 2026-09-16
- Decision owner: Product owner
- Authority: 同名の `.think` が決定の正本。この Markdown は日本語の内容投影。
- Related: 受入済みキャラ作成要件 v5 R2/R3、共通基盤要件 v3 F1、実装設計 revision 6、計画 revision 8、PERT `cc304`、ADR-0034

## 背景と根拠

受入済み要件は、キャラ修正で変更範囲を解決し、その範囲内でのみ依頼を既存 V3 より優先し、一回の試行に範囲を固定する（E1）。受入済み設計は選ばれた領域と依存領域の処理を定義するが、自然文から領域を決める手順は定義していない。通常の `POST /api/characters/:id/chat` は本文の `message` のみを受け取り、現在の focused 外見経路はテスト専用の `buildRoutes` 設定を渡した時だけ動く（E3）。既存の scope/Ollama 実験は評価専用の未 Seal WIP で、製品仕様や合格根拠ではない。

所有者は、テスト条件として外見を固定することは許容し、製品の修正機能を外見に固定せず、依頼文に従って範囲を決める方向を示した（E2）。その後の「進めてください」はこの候補を進める指示であり、この ADR の正確な revision 2 を受入れた記録ではない。

## 判断軸と選択肢

製品の依頼文を保ち、関係ない領域を誤って変更せず、候補の確認までは現行キャラを変えないことを優先する。考慮した案は次の三つ。

1. ユーザーに領域を選ばせる。判定処理は少ないが、テスト上の制御を製品操作へ移し、自然文だけの依頼を変える。
2. 外見へ固定する。今回の試行は容易だが、他領域の依頼を誤って扱う。
3. 自然文から provider が有界の範囲候補を提案し、サーバーが検証・固定する。通常の依頼文を保てる一方、推定処理一回分の実装、計数、失敗経路が増える。**この案を提案する。**

## 提案する決定

**D1 — 入口。** 通常の所有者向け修正依頼は `message` のままにする。focused V3 revise が有効な場合、依頼文から変更対象の意味領域を provider-assisted の有界な作業として提案させ、サーバーが検証する。この作業も同じ試行の資源計数に含める。キャラ内容の提案を始める前に、解決した領域を不変の元 V3・依頼文とともにその試行へ固定する。ユーザー必須の領域選択 UI/API や、製品全体の外見固定値は追加しない。テストでは外見を固定してよいが、それは範囲推定が働いた証拠ではない。

**D2 — 最初の試行の限界。** cc304 では、変更範囲が明確で単一領域の依頼だけを進める。曖昧、無効、または独立した複数領域にまたがる依頼は、推測や従来経路への無言のフォールバックで候補を作らない。無効な応答は技術的失敗であり、所有者への質問にはしない。曖昧な依頼で質問できるのは受入済み R13 の条件を満たす場合のみで、それ以外は有界の失敗とする。複数領域の依頼は今回の試行では扱わない。公開結果の正確な形は通常経路の実装前に後続設計で定める。この試行の制限を最終製品全体の仕様とはしない。

**D3 — cc304 で見る結果。** 範囲が明確な外見の文章設定一件を、通常の所有者 HTTP 依頼から、ローカルの制御された provider 応答、既存 worker・kernel・adapter、永続化、所有者向け差分確認まで通す。現行 V3 generation と pointer は変更しない。顔画像、最終受入、create、migration、有料 provider 呼び出し、配備、pointer 有効化は今回の対象外。固定範囲の診断テストや未 Seal 実験だけを、自然文判定の合格根拠にしない。

## 影響と残る判断

依頼文を使った通常入口の試行が可能になる見込みだが、範囲推定・計数・失敗経路の実装が増える。単一領域以外の依頼は今回完成しない。曖昧なときの所有者向け応答と、後続の複数領域対応は別途判断する。局所試行の成功は、一般的な出力品質、製品受入、配備可能性を証明しない。

## 互換性・移行

リクエスト本文に必須の選択フィールドは増やさない。既存 V2 や古い試行の意味は書き換えず、データ移行も行わない。新経路の有効化・切替条件は後続設計で定め、この提案だけで配備済み経路を切り替えない。

## 検証と権限境界

自然文から解決した領域、試行に固定した範囲、保存候補と差分、現行 pointer 不変を一件の実経路で確認する。曖昧・無効・複数領域の依頼が勝手に別領域の候補にならないことも対象とする。合格根拠にするテストは、正確な source と現行 Cause chain を持つ Seal が必要である。固定範囲の診断テストだけでは自然文判定を証明しない。

2026-09-16、所有者に日本語の全レビュー範囲と正確な revision 2 を提示し、受入を尋ねた直後、「進めてください」と回答を得たため **Accepted** とする。単一領域に限る初回試行と、その他の依頼を非成功にする判断もこの受入範囲に含む。受入が認めるのは D1–D3 のローカル実装範囲であり、有料 provider 呼び出し、候補の最終受入、pointer 変更、配備、リリースは認めない。
