# ナレータ入力圧縮方針 第1版

決定日: 2026-10-06。状態: 所有者が入力圧縮方針を採用。実装は未着手。

## 要件と対象

所有者は、潜在側の方針を保存した後に提示した「実況の回数や文章量を変えず、入力の重複を減らす」案に対して「では、それで進めましょう」と指示した。本書はナレータの入力に関する合意と、その実装へ渡す設計を記録する。

対象は実況LLMへの送信資料と共通指示の圧縮。モデル、呼び出しタイミング、batch上限、待機期限、再試行、実況の公開単位・出力量、正準状態の裁定は変更しない。呼び出しの間引きやイベントの統合はこの合意に含めない。

rc17公開試合は実況25回、平均入力約8,491トークン、入出力合計218,904トークン。抽出した戦闘receiptの固定systemは11,751文字、userは約7,758〜8,301文字だった。文字数はトークン数ではなく、これらはdispatch時に加わる認知・公開済み資料と出力契約を含まない。削減量は未測定。

## 入力の構成

1. 場面: 視点から参照可能な位置、姿勢、身体の状態、現在の環境。変化がなくても今回の出来事を理解するために必要な状態は残す。
2. 出来事: 今回の行動の試み、観測できる結果、確定した変化。失敗・未確定・帰属不明を成功や特定人物の行為へ書き換えない。
3. 発言: 今回の確定した台詞を話者とともに原文で渡す。
4. 認知と連続性: この視点に許された認知、直前から続く要点。過去実況の全文を繰り返す代わりに、対象参照・既知事項・直前に描写済みの要点を短く渡す。
5. 描写方針: 今回必要な外見・呼称の制約と文体。プロフィールは描写上の制約であり、知覚された出来事や内面の公開許可にはしない。

自然文の段落と箇条書きを用いる。入力JSONを全項目そのまま文章化する方法をやめ、実況に必要な意味を投影する。出力JSONと機械による検証は維持する。

## 省略と保護の境界

省略対象は、今回に関係しない人物背景・能力一覧、同一事実の複数箇所への再掲、資料を読むための冗長な構造説明、重複する指示である。

残すものは、発言原文、行動の試みと結果の区別、因果が確定している範囲、継続中の負傷・状態・位置、結果を理解するための環境、呼称と外見の整合、認知範囲、未特定の対象、receiptの識別・順序・phase、出力に使う対象参照である。出力契約とresponse schemaの整合も保持する。

内面描写が許される視点では、既存の投影が許した内面の要点を残す。外部視点へ私的な動機や潜在状態を追加しない。「キャラ情報を省く」を全視点の内面描写禁止へ拡張しない。

過去実況全文を省く際は、既出描写の反復防止と認知の継続に必要な情報を保持する。現在の公開済み資料を単に切り捨てるだけの実装にはしない。

## 基本設計

型付きの確定資料 → 視点に沿った実況用投影 → 短い自然文 → LLM → 既存の厳密な出力検証、の依存方向にする。

- 投影層は必要な事実・参照の選択だけを担当し、行動の成否や新しい因果を決定しない。
- 文章化層は投影された事実を短く配置し、意味を補ったり実況を創作したりしない。
- 共通指示はbatchで一度だけ渡し、receiptごとは識別情報・資料・phase固有の差分を渡す。異なる文体・視点等がある場合は安易に共通化せず、それぞれの束縛を守る。
- 既存の発言照合、receipt coverage、認知参照の検証は独立した責務として維持する。
- 圧縮そのものに毎回の追加LLM呼び出しは導入しない。継続要点は既存の型付き認知・確定資料から構築する。決定的な抽出で意味を保持できない資料は必要部分を残す。

## 詳細設計へ渡す項目

現在の入口は `backend/src/llm/awareness-narration-phase.ts`、phase資料の生成は `openai-compatible.ts`、dispatchは `awareness-frozen-narration.ts`、許された認知の契約は `awareness-narrator-context.ts`。既存の資料・投影・出力契約を確認したうえで、圧縮投影の型と自然文rendererを別責務に分ける。

未決定なのは、継続要点の厳密な型と上限、phaseごとの投影項目、既存の凍結済み資料への適用方法、プロンプト改訂の束縛・保存形式である。既存Accepted ADRの不変束縛と最新版指示への統一を照合し、必要な改訂を実装前に記録する。本書だけで保存済み資料を改変しない。

## 検証と完了条件

全phaseと複数receiptについて、圧縮前の許された意味を維持し、発言原文・結果・知覚境界・未特定の対象・認知参照・receipt対応を保持することを検証する。背景の削減が外見の矛盾や内面の漏洩を起こさないこと、負傷や決着の原因が落ちないことも確認する。

同一の凍結資料で送信文の文字数を比較し、実利用時にはSDKが報告した入力・出力・合計トークンを記録する。文字数から実トークン削減を断定しない。削減率や厳密なトークン上限はまだ採用していない。

本書の保存は設計方針の記録完了であり、実装・公開環境での削減達成ではない。次の確認点は、全phaseの入力項目と既存ADRに対する詳細設計の照合である。
