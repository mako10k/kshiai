## 目的と到達条件

最初に所有者が Stage で使う対戦は、新規 V3 キャラクタ Neva 対 Rio の一戦とする。新規作成は V3 同士に統一する。Stage への切替前に始まった未完了対戦は物理削除し、HTTP・対戦状態の再送と非同期 worker からの復活を防ぐ。完了済み対戦の履歴と記録済み世代は保持し、切替後も読み取れるようにする。V2→V3 キャラクタ移行の Stage 試行は後続の `cc316` に置く。

親の `cc305` は対象データと関連記録、切替順序、受入要件・後継 ADR、見積りの根拠をレビューする。子の `vt102` は両者の不変 V3 binding と、作成・読込・進行・再送・破棄の共通境界を実装する。`vt103` は新規 V2×V2・混在の拒否、V3×V3 の完走、旧・未完了対戦の破棄と完了済み履歴の保持をローカルで確認する。`vt108` は別の Stage データ操作権限を得た後に、正確な対象と関連記録を確定して物理削除し、全経路の読戻しを行う。専用到達点 `VST_CUTOVER` から `VST_STAGE_READY` への gate は、破棄の読戻しと両キャラクタの Stage 準備を揃えてから実プレイへ進める。`vt105` の配備と `vt108` の切替は、V3-only 公開の一つの確定点として順序・競合・回復を事前に固定する。

`CS_STAGE_TRIAL R3`、`CS_MIGRATED_STAGE_TRIAL R2`、`CS_FINAL R2` は、完了済み履歴の保持と切替前の未完了対戦の破棄を区別する。従来の到達条件と task 実績は履歴として維持する。`vt102` は suspended を維持し、切替要件と後継 ADR の Accepted revision を確認してから再開する。新しいアーキテクチャの実装はこの受入に依存する。要件候補と設計候補の受入は、それぞれの正本で記録する。

## 見積りと次の測定

子計画の旧 13 Point に `vt108` を追加した。`vt108` の 1／2／4 Point は関連行数を読む前の専門判断による暫定範囲であり、期待値は 13/6 Point。DEV 一名の resource schedule は **91/6 Point（約15.2 Point）**、親 `cc305` の 1 Point を含む初回 Stage 経路は **97/6 Point（約16.2 Point）**。`cc314` は子計画の roll-up であり、追加工数として二重に数えない。旧 14 Point との差 **13/6 Point** は追加した切替作業である。

`vt102` の既存 3／4／5 Point は、境界整理前の見積りである。ライフサイクル境界の追加費用は未計測なので、約16.2 Point と以下の日付は **既知範囲の暫定下限**として扱う。直近の小規模完了作業から観測された 3 Point／実働日を転用し、9月29日開始、土日を休み、祝日と外部待ちを算入しない場合、初回 Stage 経路の内部作業は **10月6日ごろ**、親計画全体の残り 27.2 Point は **10月12日ごろ**。半速 1.5 Point／実働日では、それぞれ **10月13日ごろ／10月23日ごろ**。これは Stage 配備・データ操作・所有者受入の待ち時間を含まない。

最初の更新点は 2026-09-29。`cc305` で対象環境の未完了対戦と非 cascade 関連記録を読み取り、`vt102` の最初の実経路作業の開始・終了を計測して、`vt102` と `vt108` の残量および親子の工程を更新する。Stage 読取に必要な接続先と権限は、その実施前に固定する。利用者が Stage で使える機能は現時点で増えていないが、破棄作業を初回試行の必須経路に入れたことで、切替後の挙動を観測可能な完了条件へ結び付けた。
