# キャラクタV3移行計画 revision 9 — 目的と最初の試行を結ぶ

- Status: Accepted（2026-09-16、所有者がrevision 9の現行計画への採用とcc304の再開を明示確認）
- Date: 2026-09-16
- 現行PERT: `docs/character-semantic-migration.pert`
- 前版: `docs/character-semantic-migration-plan-revision-8-proposal.md` とGit履歴上のrevision 8 PERTを保持する。
- 根拠: 所有者が示した「V3を試したい → V2キャラが使えない → V2をV3へ移行 → 構造化基盤 → スコープ自動推定」という目的連鎖、およびStageで移行済みV2キャラを実際にゲームで使うことを最初の通過点とする確認。受入済み構造化基盤要件、V3キャラ要件、ADR-0031、ADR-0035、計画revision 8の安全な試行順を維持する。

## 目的と到達点

最初の利用者価値は、所有者が選んだ厳密なV2元データからV3 generationを作り、所有者が受け入れたそのgenerationをStageの実ゲーム経路で使い、ゲームがそのV3 generationに結び付いたことを確認できること。候補の生成、差分表示、テスト成功だけではこの到達点に届かない。これは本番の全キャラ復旧やschema-3作成・修正切替より前の**途中通過点**であり、最終ゴールの代用ではない。

| 所有者の目的連鎖 | revision 9の対応 |
| --- | --- |
| V3を既存キャラで試す | 中間milestone `cm314`、実Stageゲーム試行 `cc314`、`CS_STAGE_TRIAL` |
| V2キャラはそのままではV3で使えない | 厳密なV2 sourceからV3へ移す `cc312`、一件のowner操作の局所確認 `cc315`、Stage移行・受入・使用 `cc314` |
| 共通の部分的構造化基盤を使う | 一つの基盤を `revise` `create` `migrate` に順次通す `cc304` `cc311` `cc312`。三モード全体の回復経路 `cc313` は初回試行後に確認する |
| 自然文から構造化スコープを推定する | ADR-0035に従う通常HTTP入口のprovider-assisted判定を `cc304` と `CS_REVISE_SCOPE` に明記。テスト固定スコープは代用しない |
| V3運用と全件復旧を完成する | 中間試行の後に広いR20評価 `cc306`、本番コード配備 `cc307`、対象復旧 `cb209`–`cb213`、最終切替 `cb214`／`cm114`を維持 |

## 目的への既知の最短工程

現行の安全な試行順を保ち、残る局所経路は `cc304 revise → cc311 create → cc312 migrate → cc315 一件に必要なowner操作 → cc305 Stage候補確定 → cc314 一件の実Stage試行` とする。元の `cc306` はStage配備と広いR20評価を一つに含み、移行候補をnon-currentのまま評価するため、完了しても「移行済みキャラをゲームで使う」結果にはならない。revision 9では初回試行のStage配備・一件の移行・ゲーム使用を `cc314` に切り出し、広いR20コーパス評価 `cc306` をその後へ移す。三モード全体の回復経路 `cc313` も初回試行の後へ移す。R20全体や本番配備・全件復旧を初回試行の前提にしない。

`cc304 → cc311 → cc312` は「基盤の対象が三モードであり、機能的に問題がなさそうな案から試す」という受入済み順序を保持したもの。移行データ変換に修正・生成の完成が技術的に必須だという主張ではない。`cc315` は初回Stage試行に必要な一件のowner受入・選択経路に限り、`cc313` の全モードの未観測分岐を先回りして増やさない。結果によって不要な作業が判明すれば、次の実行前に経路を再評価する。既知の制約の下で不要な先行工程を置かないという意味での「目的最短」であり、未知の障害を含む絶対最短時間や納期の保証ではない。既存のpointは納期見積りではない。

## 初回Stage試行の境界

- Stageで対象となるV2 sourceの有無と正確なidentity、既存Stageへの持込み要否は未確認。利用可能なsourceがなければ実試行を成功扱いせず、source準備の権限・プライバシーを別途判断する。本番データの無断コピーは行わない。
- Stage revision、provider routeと予算、移行候補の所有者受入、Stageに限るpointer変更、ゲーム操作、停止条件と復旧経路はそれぞれ実行前の別権限に従う。この計画の採用はそれらの実行許可ではない。
- Stage試行では移行receipt、元と新generation、Stage current pointer、ゲームのbound generation、旧generationと履歴試合の読取、本番identity・pointer不変を読み戻す。
- 失敗時は自動再試行や本番への波及をせず、実際に欠けた前提を記録して再計画する。固定fixture、non-current候補、Stage health、緑のテストをゲーム使用の代用にしない。

## revision 8との差分と残る判断

- `cm314`／`cc314`／`CS_STAGE_TRIAL` を追加し、広いR20評価 `cc306` を初回試行の後に置く。
- 一件のStage試行に必要なowner経路を `cm315`／`cc315` として切り出し、三モード全体の回復経路 `cc313` は試行後に置く。
- `cc304` と `CS_REVISE_SCOPE` に自然文からの判定・同一試行内の計数を明示する。
- `cc305` の初回試行前準備からR20全体の基準決定を外し、その準備を `cc306` に移す。
- `cm114` の本番最終ゴールと既存の復旧・切替工程は削除も達成扱いもしない。
- 未確認なのはStage対象V2 sourceの存在、Stage-only受入・pointer経路の現状、必要なprovider費用、実試行に要する時間。これらを都合のよい値で埋めず、実行前に確認する。

計画の採用だけではエンドユーザーの実現価値はまだ0。残る最初の価値ゲートを、広い証明作業ではなく一件のStageゲーム使用として識別できることが将来価値への寄与である。所有者がこの計画とともに認めた実行範囲はローカルのcc304再開までであり、有料呼出し・配備・データ移行・pointer変更・commit/pushは含まない。
