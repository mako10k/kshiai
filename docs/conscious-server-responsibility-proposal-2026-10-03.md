# 顕在判断の負担軽減とサーバー責務の再設計案

2026-10-03。修正案の検討であり、ゲーム実装・本番設定は未変更。
方向の根拠はユーザー指示（LLMの判断負担軽減、サーバーの事前準備・補完・継続、意味のパターンマッチング禁止、欠落とnullの互換、具体的な修復情報）と[最新RCA](conscious-required-fields-rca-2026-10-03.think)。既存ADR-0028の目標固定・判断所有権は維持し、毎回の応答契約・修復境界の変更を[Proposed ADR-0047](adr/0047-phase-scoped-conscious-output-and-mechanical-completion.md)として整理する。

具体化: [動的な出力対象・修復・差分適用の詳細設計](conscious-dynamic-output-design-2026-10-03.md)。フェーズ別スキーマは上位の制約とし、実際の出力はGenerationPlanで今回必要な部品に絞る。

## 1. 責務の原則

LLMは、まだ決まっていない意味内容（初期目標、現在の意図、選択、発言、自由行動内容）を判断する。サーバーは、すでに決まった状態を保持し、合法候補と観測を準備し、既知の選択結果を型付きの実行値に復元し、構造を検証して結果を保存する。

機械的補完は、値を新しく創作することではない。上位目標の再送不要、候補キーから束縛済みのskillIdへの参照解決、任意フィールド欠落から内部nullへの正規化は可能。一方、自由文から「防御したいはず」と行動を選ぶ、曖昧な名前を似た技に対応付ける、意図・目標・自由行動説明を定型文で埋めることは行わない。

## 2. 出力フィールドの再精査

| 現行項目 | 提案 | サーバーの責務と残るLLM責務 |
| --- | --- | --- |
| initialGoal | 未初期化時だけ必須。確定後のスキーマから除外 | 既存目標を保持。目標未確定時の欠落/nullは未解決として修復対象。勝利等を自動挿入しない |
| initialGoal.statement | 初期化時は必須 | 性格・価値・既知関係を踏まえた目標はLLMが決める |
| initialGoal.basisRefs | 初期化時に必要 | サーバーが許可済み根拠を短いキーと内容で提示。LLMは根拠を選ぶ。サーバーは所属と種別だけ検証 |
| intent.aim | 新しい意図・行動を採用する場合に必要 | 意味はLLMが決める。新提案がなければ旧採用意図を記憶として保持するが、新実行の意図として流用しない |
| intent.rationale | 毎回の必須から外す | 意図のaimとの重複、行動受理での用途、入力へ戻る負担を削減。理由文をサーバーで生成しない。旧記録は保持 |
| intent.basisRefs | 新しい意図には根拠選択を維持、説明文は不要 | 準備済みの観測/価値/候補キーを選択。候補キーから実行の出典は機械的に記録できるが、それを意図の意味的根拠と偽って補わない |
| nextAction | 通常判断では省略/null＝新行動提案なし。laterでは成立する具体的選択が必要 | 省略をwaitに変換しない。laterの欠落は修復対象、失敗後の既存fallbackはモデル判断とは別に記録 |
| nextUtterance | 任意。省略/null＝この応答から発言提案なし | 既存発言を再発話しない。無発言という内面的意思を証明したとは記録しない。非null不正値は黙ってnull化しない |
| realizedManifestation | 候補なしならスキーマ/入力から除外。候補ありなら任意の候補キー | 省略/null＝新しい発現提案なし。選択はLLM、キーから既存候補への復元はサーバー。自由文一致の課題を減らす |
| turn / phase / revision / actor / contractVersion | 出力に要求しない | サーバーが呼び出しコンテキストから付与。モデルが状態を選択/書換えしない |
| 行動のskillId・候補内の固定メタデータ | LLMによる転記を不要にする候補キー方式 | サーバーが今回の候補表から完全な型付きIntentを復元。キーの完全一致で参照解決し、名称から推測しない |
| 自由行動description/対象/desiredOutcome、reflectの分析/指針 | 新しく必要な意味内容はLLMに残す | 能力の存在だけで内容は作れない。候補キーの選択だけで情報を補ったことにしない。動的内容のkind別検証は維持 |

intent全体も通常判断では省略/nullを許す。ただし、行動が非nullなら意図とその根拠が必要。「行動だけ返したので意図は旧状態から補う」は採らない。意図のみ・行動なしの提案は現行の発言主体の判断を維持できる。両方ない場合は新しい判断レコードを作らない。

## 3. 今回の契約だけを渡す

サーバーが `phase`、目標の有無、発現候補の有無、候補表から今回の出力契約を確定する。全フェーズの説明を一つのプロンプトへ併記しない。

- 目標未確定: initialGoalと今回の意図・行動・任意表現。独立plannerを増やさず、既存の判断callで初期化する。
- 目標確定後の通常判断: 意図・行動・任意表現。initialGoalは出力対象外。
- later: 意図・具体的行動のみ。発言や目標の再生成を要求しない。
- aftermath: 任意表現のみ。戦闘判断の規則・候補・目標初期化ポリシーを渡さない。
- 表現候補が空: 表現選択フィールドと候補一覧を省く。

出力の処理順序を単一の契約記述から生成し、プロンプト・APIスキーマ・受信正規化・検証を別々に手書きして乖離させない。プロバイダーの厳密スキーマが任意プロパティを許さない場合は、該当する少数のキーをnullableとして表現する。受信側では許可済みの任意キーに限り省略とnullを同じ内部値に正規化する。厳密スキーマの制約を満たすために別フェーズの不要キーを復活させない。

## 4. 欠落・null・不正・継続を区別する

| 状態 | 処理 |
| --- | --- |
| 初期化済み目標 | 同一の保存値を保持。LLMに再出力させない |
| 任意表現の省略/null | 新提案なしに正規化。不要な再試行をしない |
| 通常の意図/行動とも省略/null | 新提案なし。旧latestDecisionは過去の記憶として保持し、新しい行動の意味に転用しない |
| 行動あり・意図なし | 意図の欠落として修復。行動kindからaimを合成しない |
| 初期目標未確定で省略/null | 未初期化を維持し、修復。固定の勝利目標を入れない |
| laterで行動省略/null | 必要な具体的選択の欠落として修復 |
| 非nullの型不正/無効参照 | 任意であっても不正。nullへ黙って変換しない。独立した有効フィールドの扱いは保持 |
| 現在候補にない選択 | 正確な不成立理由と現在候補を返す。古いキーを似た候補へ対応付けない |
| 修復上限後の失敗 | 未解決を記録。既存機械的fallbackは由来を明示し、古い意図・発言と結び付けない |

省略/nullの処理結果は互換にしても、診断には `omitted` / `explicit_null` を保持する。「LLMが沈黙を選んだ」と「提案がなかった」を混同しない。正規化はフィールドの存在・型・完全一致の参照表に基づく。自然言語・正規表現・類似度で意味を補わない。

## 5. 事前準備と入力削減

機械的な候補可否（現在の資源、cooldown、射程、規範、装備、凍結済みasset情報）を既存の権威ある評価関数で計算する。最終実行時も再検証する。準備が意味推定を必要とする自由行動能力を、完成した行動と混同しない。

自己情報・相手の観測・使用可能能力を、今回判断に必要な型付き投影で渡す。目標確定後は目標文と今回の観測を提示し、初期目標導出の長い手順を再掲しない。後日談には戦闘判断の説明を持ち込まない。必須規範・未知情報の境界は削らない。文章中の単語で「重要そう」な情報を抽出することは行わない。

候補表は現在の呼び出しコンテキストに束縛されたキーとする。既存のcanonical IDを持つものは再利用し、必要なローカルキーは一意な表から解決する。キーの意味を推測する必要はない。表の基準はサーバーのphase/revisionに紐付け、別の判断へ持ち越さない。

## 6. 低負担な修復

提案上限は、一つの論理判断につきアプリケーション修復1回。HTTP再試行やprovider fallbackでこの上限をリセットしない。実装前に記録・費用・phase境界と上限の扱いを確定する。

再試行では、既存の許可済み凍結コンテキスト、前回のデコード可能な応答、修復対象、短い具体的診断を渡す。モデルに全文から誤りを探させない。例として、利用不能キーなら以下のような構造情報を提示する。

```json
{
  "repairFields": ["intent", "nextAction"],
  "errors": [{
    "path": "/nextAction/choiceKey",
    "code": "not_in_current_candidates",
    "received": "candidate-old",
    "allowed": ["candidate-current-1", "candidate-current-2"]
  }],
  "preserveFields": ["nextUtterance"],
  "instruction": "修復対象だけを返す。候補キーをそのまま選び、採用済みの内容は書き直さない。"
}
```

上の候補キーは説明用の仮値で、実際にはサーバーの候補表の値を渡す。スキーマ違反には期待型・欠落パス・必要な情報を、参照不備には許可された短いキーと対応する内容を渡す。scope外の私的情報、長いスタックトレース、別フェーズの説明は付けない。

依存関係にも注意する。自由行動から別の行動へ選び直す等、意図まで意味的に変わる場合は修復対象をintentとnextActionの組へ広げる。サーバーが「同じ意味」と文章で判定しない。行動選択の変更ではこの組を保守的に再提案させる。それでも発言は既存の独立受理方針を維持する。

修復応答は指定された閉じたフィールド集合だけ。受理済み表現を上書き・再発話しない。未採用部分へmerge後、通常と同じスキーマ/参照/候補/規範検証を行う。JSONが壊れて部分復元できない場合は、正規表現で拾わず、現在の最小契約全体を再生成させる。修復中にCAS基準が変わった場合は、その結果を古いコンテキストへ適用せず、既存のフェンス/再開規則に従う。

## 7. 移行と検証

旧記録・旧入力・凍結済み試合の契約を上書きしない。新しい判断契約版と凍結tupleを追加し、新規試合へ明示的に適用する案を基本とする。継続試合への移行は別途決定する。旧rationale等の履歴も削除しない。内部型をcastで合わせず、新しい型付きの意図・出力・正規化結果を用いる。

実装の受入条件は、フェーズ・目標有無・候補有無ごとの最小スキーマ、任意の欠落/null互換、意味必須項目の欠落拒否、未知キーと非null不正の検出、候補表からの完全復元、自由行動/reflect内容の保存、修復の依存関係・回数・CAS・独立表現の維持。性格・関係別の目標妥当性は別の意味評価で確認する。

運用比較では、入力/出力トークン、呼び出し数、修復率、判断採用率、待機比率、行動の反復、自由行動成立、発言の反復を測る。必須キーが揃うことだけで品質改善を宣言しない。
