## 変えない目的

最初の通過点は、所有者が選んだ正確なV2元データをV3へ移し、所有者が受け入れたそのgenerationをStageの実ゲームで使い、ゲームがそのV3 generationに結び付いたことを確認すること。候補生成・テスト成功・Seal整備だけでは到達しない。本番の全対象復旧とschema-3 authoring切替は、その後の最終目標として残す。

「V3を試す → V2キャラの移行 → 共通の部分的構造化基盤 → 自然文からの変更範囲推定」という目的のつながりを維持する。機能を試す内部順序は、既に受け入れられた `revise → create → migrate` のまま。create/reviseの完成がデータ変換一般に必須だという新しい主張はしない。

## 進行・報告の4つの単位

| 単位 | 到達点と目的への関係 | 内部工程・現状 | 判断境界 |
| --- | --- | --- | --- |
| M1 根拠を現行化する | 既存の計画・実装・テストを何の根拠で使えるか明確にし、移行作業を再開できる状態へ戻す | `cs316`。上位要件・ADR・設計の限定修復は済み。全REFの用途分類と下流consumer照合は残る | 個別Lunaレビューを内部で継続。新rootは本人レビュー対象を集約。仕様判断は別途本人判断 |
| M2 移行をローカルで通す | 共通基盤で自然文revise、create、V2移行と一件に必要なowner操作の経路をつなぐ | `cc304 → cc311 → cc312 → cc315`、到達点 `cm315`。今はM1待ちでcc304をsuspendedとする | 固定scope試験を自動推定の代用にしない。各工程の既存権限を確認し、計画修正を後続実装の新規許可としない |
| M3 StageでV3を実際に使う | 所有者が欲しい最初の利用体験を得る | `cc305 → cc314`、到達点 `cm314`。未達 | exact revision、providerと予算、配備、候補受入、Stage pointer変更等の既存別認可を維持 |
| M4 全体評価と本番復旧を終える | 一件の試行を全体適合や本番復旧の代わりにせず、受入済み最終目標まで進める | `cc313 → cc306 → cc307 → cb209…cb214`、最終 `cm114`。未達 | R20基準・費用・本番操作・対象候補受入・最終切替の別判断を維持 |

この4単位は報告・継続のまとまりであり、新しい製品完了条件ではない。M2〜M4はPERTのtask tagsにも対応付ける。内部task ID・依存関係・duration・既存work_event・milestone criterionとcommitmentは保持し、履歴を圧縮・削除しない。広いR20評価や全モードの未観測回復分岐を、初回Stage試行の前へ移さない。

通常の文書確認・既存承認内の非root修復ごとにターンを止めて継続許可を求めない。レビューの実施単位とユーザーへの報告単位を分離する。本人判断が必要な新rootや仕様変更は、比較可能な候補をまとめて提示する。ただし判断待ちの内容を先に実行することはない。無関係な判断待ちが独立して許可済みの作業まで止めることも避ける。

- 別途、全体ADR検査では変更していない0015/0016/0017/0019に形式・受入記録チェックのエラーがある。残件として調べるが、検査エラーだけで既存仕様を変更したり、依存関係を確認せず移行機能の新しい完了条件にしたりしない。

### 見積りと現在の停止状態

M1の残量・期間は未確定。PERTのstrict taskはduration必須なので、架空のpointを付けず未見積Work `cs316` として保持する。Workだけではstrict DAGの実行前提にならないため、`cc304`の状態を `active` から `suspended` に直し、M1未完了という理由を記録する。これは既存の「まずSealをすべて健全化」の優先状態を計画へ反映するもので、過去の実装・実績を取り消すものではない。既存work_eventは不変で保持し、状態整合のため今回の計画上のholdを記録した実測時刻（2026-09-17 19:29:37 JST）でsuspendイベントを1件追記する。元の中断時刻を遡って推定した記録ではなく、過去の活動時間や工数を主張しない。この時刻から過去の実働時間を逆算しない。

M1完了後は根拠・対象・既存権限の現在適合を確認してcc304を再開する。この改訂では再開を実行せず、cc311以降の実装や外部操作へ新しい実行権限を与えない。既存duration/velocityも納期保証ではなく、M1未見積分や別承認待ちを含まない数値から到達日を約束しない。

## 根拠と変更範囲

現行の上位根拠は、固定された共通基盤v3・キャラv5、ADR-0032（0031の影響されない決定を継承）、0033、0035とAccepted実装設計rev6。exact Seal対応は健全化記録の表を使う。旧workflow全文のsupersessionを尊重し、0031自体を単独の現行ADRとして復活させない。計画はこれらを実施順へ落とす下位文書であり、上位仕様を再定義しない。

revision 9から変えるのは、進行単位、現時点の根拠・残件、cc304の実行待ち状態、PERTの現行改訂記録への参照だけ。既存の `CS_FINAL`、`CS_CONNECTED`、`CS_EVALUATION`、`CS_STAGE_TRIAL`、`CS_REVISE_SCOPE`、`CS_PRODUCTION` は本文・revision・commitmentを変えない。done/reachedは当時の記録として残し、今回の計画修正によって現行の有効証拠へ再昇格したとは扱わない。

この改訂自体のSeal根拠照合もM1の対象であり、ファイルを変更しただけで「現行Seal済み計画」とは報告しない。上位9REFの健全性と、改訂計画のSeal状態は別である。
